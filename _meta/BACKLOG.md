# Task Backlog

> **`_meta/` charter.** This folder holds live, mutable, maintainer-facing project
> *state*: trackers, queues, and manifests of work. Durable reference and the design
> record live in `docs/` (specs, decisions, handoff, retro, research). Today the only
> artifact meeting that bar is this backlog, and that is expected, not a gap.
>
> **Do not add** to `_meta/`: a `ROADMAP` (the v2-candidates + parking-lot tiers below
> are the roadmap), a `SCHEMAS` file (the backlog schema lives in this file and in
> `docs/architecture.md`; schemas belong next to their artifact), a `LAB_LOG` (use
> `docs/handoff/` + `docs/retro/`), an ADR index (`docs/decisions/` self-indexes by
> number), or `checks/`/`infra/` (that is `tests/` + `.github/`). An `INVENTORY`
> manifest is allowed *only* if it becomes the single source `tests/test-meta.sh` and
> the README derive from, never a hand-maintained fourth copy. Resist the junk drawer.

The kit's single source of truth for "what's left to do." Three tiers, decreasing commitment:

1. **Active queue** - committed work, each with a stable `ID-NNN` id and a status. This is what `/user:start` and `/user:next` read when you ask "what's left?". Shipped items drop off the queue (the CHANGELOG is the canonical "what shipped" record).
2. **v2 candidates** - not committed; become real only after a spec is written and `/spec-validate` passes. Listed for visibility.
3. **Parking lot** - revisit only if a real usage signal arrives.

Completed cycles live in `docs/handoff/v<version>.md` (build notes) and `docs/retro/v<version>.md` (cycle retros). Per-release CHANGELOG entries are the canonical "what shipped" record. Completed work is NOT mirrored back here, to avoid drift.

> Schema note: the column + status-vocabulary contract is formalized in the **[Schema](#schema)** section below (SPEC-005 / ID-006). The session-start rendering of this queue is wired in SPEC-006.

## Active queue

Status vocabulary: `queued` (committed, no spec yet) -> `claimed` (pulled by a session via `/kit:assign --next`; the cross-session claim lives in `lib/goal-registry.sh`, this records the board state; render/flip mechanically with `lib/backlog.sh board|next|set`) -> `speccing` (spec being drafted) -> `validated` (spec passed `/spec-validate`) -> `executing` (in build) -> `shipped` (drops off, see CHANGELOG). Off-ramps: `parked` (a drafted spec deliberately set aside; the spec holds its own revisit note) or `dropped` (deliberately cleared from the active path during a re-evaluation; a one-line reason in the Status cell; the ID retires and is never reused).

Lane = the WORKFLOW.md risk tier (`tiny` / `normal` / `full`).

## Schema

The Active-queue contract (formalized per SPEC-005 / ID-006; the charter keeps the schema in this file, not a separate SCHEMAS file).

| Column | Meaning |
|---|---|
| `ID` | `ID-NNN`, zero-padded, stable, assigned on entry, NEVER reused. |
| `Title` | one-line description of the work. |
| `Source` | where the item came from (a braindump item, a research finding, a dogfooding signal). |
| `Target artifact` | the spec or doc this becomes (`SPEC-NNN`, or `(tiny, no spec)`). |
| `Lane` | the WORKFLOW.md risk tier: `tiny` / `normal` / `full`. |
| `Status` | the lifecycle state below. |

**Status lifecycle:** `queued` (committed, no spec) -> `claimed` (pulled via `/kit:assign --next`) -> `speccing` (spec drafting) -> `validated` (spec passed `/spec-validate`) -> `executing` (in build) -> `shipped`. Off-ramps: `parked` (a drafted spec deliberately set aside; the spec holds its own revisit note) or `dropped` (deliberately cleared from the active path during a re-evaluation; a one-line reason in the Status cell; the ID retires and is never reused). SHIPPED items drop off the queue: the CHANGELOG is the canonical shipped record and completed work is not mirrored back here.

**Consumer:** `/user:start` and `/user:next` render this queue when you ask "what's left?". That rendering is wired in SPEC-006, not here; SPEC-005 pins only the schema the spine reads.

This is **not** `TODOS.md`: that file is gitignored, transient, per-diff `/review` output, not the backlog. See the state model in `docs/architecture.md`.

## Parking lot (revisit if a real signal arrives)

- L5 orchestration (Nimbalyst integration). (2026-05-23 re-scope per ADR-0022: the boundary no longer sits at "3+ concurrent sessions". One operator's N concurrent same-machine sessions over disjoint goals are now in-kit, coordinated by the passive running-goal registry, `lib/goal-registry.sh`, SPEC-036 / ID-040. L5 is reached only by coordination **across machines**, **3+ live human operators** sharing a pool, or **goal-ordering chains** (B waits for A to merge); those still hand off to Nimbalyst / GSD v2.)
- **In-kit DAG executor (the "build a runtime" option, Option 4).** A scheduler inside the kit that owns topological task ordering, wave execution, dependency resolution, and unattended cross-task progression. Deliberately NOT built: this is a runtime (crash recovery, state machine, per-provider error handling), which breaks PHILOSOPHY "Shallow and wide" + the bash-over-binaries thesis + the runtime-integration boundary. ID-035 (first-class parallel execution) deliberately stops short of this: it does disjoint-file fan-out + a pairwise interference gate + a wait-queue, NOT a DAG executor. **Tripwire to revisit:** when goals develop real ordering chains (C needs A+B merged, D needs C) that the interference-gate model cannot express, i.e. when "we actually need a DAG" becomes true. At that point the answer is to hand execution to GSD v2 (gsd-build/gsd-2, the external Pi-SDK runtime), not to build a scheduler in-kit. Full reasoning + the 7-option parallelism menu + the DAG analysis: `docs/research/2026-05-22-concurrent-goal-dispatch.md`.
- **Team mode ("attestation, not sync"): multi-engineer usage of the kit on one repo.** Audited 2026-07-04; three walls: the gate ledger is machine-local with no actor field (a teammate shipping a foreign-built branch hits false blocks, so the rational move is an anonymous override); enforcement is client-side Claude Code hooks only (a bare `git push` from a plain terminal bypasses it even solo; a kit-less teammate bypasses everything silently); no identity/allocation primitives (no Owner on board rows, no actor on overrides, spec-number reservation does not cross machines). Design, deliberately NOT built yet: extend the proof-of-done pattern to lane gates (ship emits the generated `docs/runs/<rid>.md` run table onto the BRANCH as attestation; the local ledger stays the source), a consumer CI action re-checking in-branch evidence (branch protection blocks; hooks become UX), `actor=` on gate rows + an Owner column, push-early spec reservation (the pushed spec-stub branch IS the reservation). Git stays the only shared medium (merge semantics = conflict resolution), so ADR-0022's L5 fence is amended, not crossed: no lock servers, no synced state. Side effect: in-repo run tables make team-wide gate telemetry readable from git alone. **Tripwire to revisit:** a NAMED second user on a real repo (lead + contractor is already the kit's stated design intent, README "the spec as the handoff unit"). Full design: ops-toolkit `research/2026-07-04-pxpipe-plannotator-improve-absorption.md` §5.

- Agent-type hooks for deep verification. Custom subagents handle this today; revisit only if subagents prove insufficient.
